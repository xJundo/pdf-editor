# PDF Editor (type sejda.com)

Application web self-hosted d'édition de PDF : l'utilisateur importe un PDF, modifie le **contenu existant** (texte en place, images), puis exporte une nouvelle version. Déploiement sur VPS Hostinger via Coolify (100% Docker, pas de Nginx à configurer — Coolify/Traefik gère le proxy et le TLS).

## Architecture (3 conteneurs)

| Service | Chemin | Techno | Rôle |
|---|---|---|---|
| `app` | `app/` | Next.js 16 (App Router, Turbopack) + shadcn/ui (preset base-nova, Base UI) + Tailwind v4 + pdf.js | UI, auth (Better Auth), API documents/versions, rendu PDF |
| `pdf-service` | `pdf-service/` | Python FastAPI + PyMuPDF | Extraction de structure (spans texte + images), application des éditions, export. **Réseau interne uniquement, jamais exposé** |
| `db` | — | PostgreSQL 17 | users, documents, document_versions |

- ORM : **Drizzle** (schéma dans `app/db/schema.ts`, migrations SQL générées par `npm run db:generate` dans `app/drizzle/`, appliquées au démarrage du conteneur `app` par `app/scripts/migrate.mjs`). Attention : la sortie standalone de Next bundle les deps serveur, donc l'image Docker installe drizzle-orm+pg séparément pour le script de migration (voir `app/Dockerfile`).
- Fichiers PDF : volume Docker `pdf_files` monté dans `app` et `pdf-service` sous `/data/files/<userId>/<documentId>/<versionId>.pdf`. Les binaires ne vont JAMAIS en base.
- Versions **immuables** : l'original importé = version 0 ; chaque export crée une nouvelle version ; toute version est réouvrable dans l'éditeur.
- PDF signés : édités comme les autres ; les champs de signature sont supprimés à l'export (aucune préservation/re-signature requise — décision validée).

## Flux d'édition (cœur du produit)

1. Upload → disque + ligne en base (version 0).
2. Ouverture éditeur → `pdf-service` extrait la structure : spans de texte (bbox, police, taille, couleur, flags gras/italique) et images (bbox) → le front superpose des calques interactifs alignés sur le rendu pdf.js.
3. Le front accumule un **journal d'opérations** JSON (modif texte, remplacement/suppression image).
4. Export → `pdf-service` rejoue le journal sur le PDF source (rédaction ciblée + réinsertion pour le texte, `replace_image`/`delete_image` pour les images) → nouvelle version.

Typographie (implémentée étape 6, `choose_font` dans `pdf-service/main.py`) : 1) réemploi de la police embarquée du span si elle s'extrait (ttf/otf/cff) ET que sa cmap couvre les glyphes du nouveau texte (`pymupdf.Font.has_glyph`) — les sous-ensembles Identity-H, qui n'embarquent aucune cmap, s'en voient synthétiser une depuis leur `ToUnicode` (voir `embedded_font_buffer`) et restent donc réutilisables ; la couverture ignore les espaces (souvent absents des subsets, rendus en simple avance par `TextWriter`) ; 2) **sinon la même police en version complète, résolue par nom de famille** (`resolve_named_font`) — un subset ne contient que les glyphes du document d'origine, donc taper la moindre lettre nouvelle fait sortir de (1) alors que la fonte est parfaitement identifiable ; 3) sinon repli sur police libre métriquement proche (Liberation Sans/Serif/Mono selon l'heuristique de nom, puis Noto/DejaVu) avec graisse/italique corrects ; 4) dernier recours base-14. Insertion via `TextWriter` (unicode complet). Retaillage : si le texte dépasse la largeur dispo (max bbox / marge droite), la taille est réduite proportionnellement (plancher 6 pt). L'appariement span↔ressource tolère préfixe de subset et espaces (`find_embedded_font`). Le rewrap multi-lignes n'existe pas (édition span par span). Les polices libres sont installées dans l'image Docker (fonts-liberation, fonts-noto-core, fonts-dejavu-core).

## Conventions

- **UI en français** (libellés : "Mes documents", etc.). Code, identifiants et commits en anglais.
- **shadcn/ui obligatoire pour l'UI** : suivre le skill `.agents/skills/shadcn/SKILL.md` (composants via `npx shadcn@latest add`, tokens sémantiques, `FieldGroup`/`Field` pour les formulaires, jamais de `space-y-*`, icônes avec `data-icon`).
- `app` est le seul service exposé (port 3000). `pdf-service` n'est joignable que via le réseau Docker interne (`PDF_SERVICE_URL`).
- Toute requête documents/versions filtre par `userId` de la session — jamais de confiance dans un id client.

Pièges : appeler `render({canvas, viewport})` (pas `canvasContext` en plus) ; les décodeurs wasm (qcms/ICC, openjpeg, jbig2) doivent être servis en statique → `scripts/copy-pdfjs-assets.mjs` les copie dans `public/pdfjs/wasm/` (hook predev/prebuild, dossier gitignoré) et `getDocument` reçoit `wasmUrl: "/pdfjs/wasm/"`, sinon les images ICC/JPX sont silencieusement ignorées. Les bbox PyMuPDF (origine en haut à gauche) se projettent en pourcentages directement sur le canvas pdf.js.

- Export (étapes 4-5) : le front accumule `edits` (spanId → nouveau texte) et `imageEdits` (imageId → delete/replace avec dataURL) et envoie un journal `EditOperation[]` (`lib/pdf-structure.ts` : edit_text, delete_image, replace_image avec image en base64) à `POST /api/documents/[id]/versions`, qui appelle `pdf-service /documents/export` : rédaction ciblée (`apply_redactions` avec `images=NONE, graphics=NONE` pour ne pas effacer images/traits), réinsertion à l'`origin` (baseline) du span, police base-14 la plus proche (`pick_font` — le réemploi des polices embarquées est l'étape 6), `page.replace_image`/`page.delete_image` (xref validé contre les images de la page), suppression des widgets signature, `save(garbage=3, deflate=True)`. Versions immuables : le service refuse d'écraser une cible existante (409).
- ⚠️ Rédaction et lignes voisines : MuPDF supprime **tout glyphe dont la bbox *intersecte*** le rectangle de rédaction, et une bbox de span va de l'ascendante à la descendante — en interligne serrée les lignes se chevauchent verticalement. Rédiger la bbox brute d'un titre efface donc silencieusement les lignes du dessus et du dessous (bug réel : éditer « INTELLIGENCE (AI) » d'un titre 55 pt sur interligne 49 pt supprimait « TO ARTIFICIAL » et « TECHNOLOGY » à l'export, sans la moindre erreur). Comme la suppression se fait par intersection, une **bande horizontale fine** à l'intérieur du span efface quand même tous ses glyphes : `redaction_rect` ne garde donc que la part de la boîte qu'aucune ligne voisine n'atteint (`page_span_boxes` fournit les voisins, les spans eux-mêmes édités sont exclus — leurs originaux sont rédigés puis réinsérés de toute façon). Ne clipper que **verticalement** : les mots d'une même ligne (producteur justifiant, un span par mot) partagent la même hauteur, ils sont écartés par le seul retrait horizontal de 0,5 pt et par le test `_NEIGHBOUR_LINE_RATIO` sur l'écart des centres. Régression couverte par `test_export.py`.
- Extraction images : `get_image_info(xrefs=True)` (images réellement dessinées), PAS `get_images` qui liste aussi les ressources périmées laissées par replace/delete ; on filtre xref 0 (inline) et les placeholders 1×1 de `delete_image`. Images de fond : une image couvrant ≥ 90 % de la page (`_BACKGROUND_COVERAGE`) est marquée `background: true` dans la structure — le canvas pdf.js la peint déjà, donc le front ne lui rend AUCUN calque interactif (`if (image.background) return null`), sinon son bouton pleine page intercepterait tous les clics destinés aux spans texte dessinés au-dessus (cas des ordonnances/templates aplatis en fond blanc + texte réel par-dessus). Les boutons de span ont aussi `z-10` pour rester cliquables au-dessus de tout calque image.
- Géométrie (étape 7) : le front expose des poignées déplacement/redimensionnement (composant `GeometryOverlay`) sur l'élément sélectionné + un mode recadrage (`CropOverlay`, fractions du cadre). Modèle d'édition : texte = `edits` (texte) + `spanBoxes` (bbox/origin/size recalculés, `boxResized`) ; image = `imageEdits` : `{delete}` | `{transform, bbox, crop, dataUrl}`. Opération journal `place_image` (`lib/pdf-structure.ts`) : `pdf-service` décode la source (remplacement base64 ou `extract_image` de l'original), applique le crop via `Pixmap`/`copy` (CMYK→RGB), `delete_image` de l'ancien placement puis `insert_image(rect, keep_proportion=False)`. `replace_image` (étape 5) reste pour le remplacement dans la bbox d'origine. Pas de contrainte de collision (limite assumée).
- Aperçu image/police fidèle (étapes 7 & 9) : `pdf-service` `GET /documents/image?path&xref` (PNG recomposé, DeviceRGB) sert une image isolée pour l'aperçu déplacement/crop, `GET /documents/font?path&xref` sert la police embarquée (ttf/otf) ; routes app cloisonnées `…/versions/[id]/images/[xref]` et `…/fonts/[xref]`. La structure ajoute `span.fontFile` (xref de police preview ou null) et `fonts[]` ; le front injecte des `@font-face` `pdffont-<xref>` et affiche l'indicateur "Identification des polices…" jusqu'à `document.fonts.load`. `preview_font_buffer` sert **en priorité la famille complète** (`resolve_family_file`, exactement la source qu'utilisera l'export) et ne retombe sur le subset embarqué que si elle est introuvable. ⚠️ Ne jamais servir le subset quand l'export résout la famille complète : un subset ne porte que les glyphes du texte d'origine et **CSS applique son repli caractère par caractère**, donc chaque lettre nouvellement tapée s'affiche dans une autre police *au milieu du mot* alors que l'export, lui, la rend correctement — c'est le symptôme d'une désynchronisation aperçu/export. Le subset de repli reste exposé s'il est adressable par caractère : soit il porte déjà une cmap unicode, soit `embedded_font_buffer` lui en synthétise une à partir de son `ToUnicode` — **uniquement si `_maps_code_to_glyph_id` l'autorise** (Type0 + `Identity-H/V` + `CIDToGIDMap` Identity ou absent) : sur une police simple ou un `CIDToGIDMap` stream, le code caractère n'est pas le glyph id et on pointerait chaque caractère sur un glyphe faux, sans la moindre exception levée. ⚠️ `xref_get_key` signale une clé absente par le tuple **truthy** `("null","null")` — un test de falsiness rejette donc à tort le cas le plus courant (`/CIDToGIDMap` omis, qui vaut Identity par défaut). ⚠️ La réversion du `ToUnicode` doit **ignorer les destinations multi-caractères** : `<00AA> <00660069>` signifie « le glyphe 0xAA dessine *fi* » ; en garder le premier point de code mapperait `f` → glyphe de la ligature, et « file » s'exporterait « fiile » (bug réel, cf. `test_ligature_destination_is_dropped`). Les `bfrange` existent en deux formes (contiguë `<lo> <hi> <dst>` et tableau `<lo> <hi> [<d1> <d2>…]`), les deux sont gérées (cas des subsets Identity-H, majoritaires — Canva, InDesign, Figma : `/Encoding /Identity-H` + `/CIDToGIDMap /Identity` ⇒ code caractère = glyph id, donc le `ToUnicode` lu à l'envers donne exactement la table manquante). ⚠️ Ces subsets sont aussi souvent dépourvus de table `post`, que l'OpenType Sanitizer des navigateurs exige : `_ensure_post_table` en ajoute une minimale (v3.0), sans quoi le `@font-face` est rejeté avec « Invalid font data in ArrayBuffer » et le repli heuristique `cssFontFamily` reprend la main silencieusement. ⚠️ Les polices **CFF nues** (`ext == "cff"`, ce que produisent InDesign & co. pour des contours PostScript — tout ce PDF WTTC est en Agenda CFF) sont lisibles telles quelles par PyMuPDF/FreeType, donc **l'export réemploie la vraie police**, mais aucun navigateur n'accepte un CFF hors conteneur sfnt : l'aperçu retombait alors sur `cssFontFamily` → `Helvetica, Arial, sans-serif` → la sans par défaut du système (DejaVu Sans sous Linux), visiblement plus large que l'original — désynchronisation aperçu/export la plus fréquente en pratique. `cff_to_otf` les emballe en OpenType (`OTTO`) : cmap reconstruite depuis les noms de glyphes PostScript du CFF via l'Adobe Glyph List, métriques depuis ses charstrings. Le format servi est celui du **buffer réellement produit**, pas l'`ext` du PDF. ⚠️ Le filtre `ext in ("ttf","otf","cff")` de `page_preview_fonts` sert aussi de garde : sans lui, une base-14 non embarquée déclencherait la résolution de famille (qui peut aller sur le réseau). ⚠️ `fonts[]` transporte `bold`/`italic` et le front les déclare sur le `@font-face` : un programme gras enregistré en face 400 se voit **ajouter le gras synthétique** du navigateur quand le span demande 700, et l'aperçu ressort plus lourd que l'original. Les polices non embarquées (base-14) restent sans preview. ⚠️ Les images à espace couleur ICCBased ne se peignent pas sur le canvas pdf.js (décodeur qcms) — limite préexistante hors périmètre 7-9 ; les images DeviceRGB (dont tous les exports) s'affichent normalement.
- Bibliothèque de polices (`FONTS_DIR`, volume `pdf_fonts` monté sur `/data/fonts`) : `resolve_named_font` déduit la vraie famille du nom PostScript du span (`parse_font_name` : retire le préfixe de subset, découpe le camelCase, isole les mots de graisse/style — `IBMPlexSans-SemiBold` → `IBM Plex Sans` + bold ; « Roman » n'est PAS un mot de style, sinon Times New Roman se fait amputer), cherche d'abord dans `/data/fonts` (indexé par famille **et** style : la table `name` id 1 donne la famille, id 2 la sous-famille — ne lire que l'id 1 range toutes les graisses sous la même clé et une demande en gras récupère silencieusement le romain), puis télécharge la famille depuis l'API CSS Google Fonts et la met en cache. ⚠️ Le User-Agent doit être **legacy** (`Mozilla/4.0`) : un UA moderne se voit servir du woff2, que PyMuPDF ne sait pas lire. Licences OFL/Apache ⇒ embarquables dans le PDF exporté. L'ordre de résolution est **clé exacte → téléchargement → repli sur le romain de la même famille** : tester le romain avant le téléchargement masquerait la graisse demandée et empêcherait de l'obtenir un jour. `font_library_index` est mis en cache sur le mtime du répertoire (il tourne une fois par police et par page à l'extraction, et reparse sinon la table `name` de tous les fichiers). Résilience : `HTTPError` (famille inconnue) → on tente la requête sans axe ital/wght ; toute autre erreur (réseau) → abandon immédiat, pas de seconde attente ; les échecs sont mémorisés dans `_UNAVAILABLE_FAMILIES` (process-local) pour ne pas payer la latence à chaque export. `FONT_DOWNLOAD_ENABLED=0` rend le service totalement hors-ligne (replis look-alike uniquement) ; les polices propriétaires non téléchargeables se déposent à la main dans le volume. Le Dockerfile doit créer *et* `chown` `/data/fonts` : un volume nommé monté sur un répertoire absent atterrit root et `appuser` ne peut plus rien écrire (échec silencieux).
- Calque texte : l'aperçu d'un span édité (et l'`<input>` inline) doit masquer les glyphes déjà peints sur le canvas, donc son fond ne peut pas être transparent. Il reste **une couleur plate**, échantillonnée sur le canvas pdf.js (`sampleBackdrop`, mémorisée dans `backdrops`) : couleur dominante d'un anneau de 2 pt autour de la bande d'encre, et à défaut de dominante à ≥ 55 % (span posé sur une photo) la **médiane** de l'anneau — dans les deux cas une vraie couleur de la page à cet endroit, jamais le repli par contraste `spanBackdrop` qui peignait une boîte **noire** sous un titre blanc. ⚠️ Une reconstruction pixel par pixel du fond (échantillonnage colonne par colonne étiré sous le texte) a été essayée puis **retirée** : elle suivait fidèlement les dégradés mais rendait sale — ne pas la réintroduire sans validation visuelle. Trois points à ne pas casser : (1) le fond est peint **uniquement sur la bande d'encre** (`inkBand` = baseline −0,82 em / +0,22 em, bornée par la bbox) via `background-size`/`background-position`, car les bbox PyMuPDF vont de l'ascendante à la descendante et se chevauchent en interligne serrée — un fond pleine bbox rognerait les lignes voisines ; (2) l'`<input>` porte `bg-transparent`, sinon la couleur de champ du navigateur repeint toute la boîte par-dessus la bande ; (3) la couleur est ré-échantillonnée à **chaque repeint du canvas** (`renderCount`, pas un booléen `rendered`) : après un changement de zoom ou de largeur, une valeur lue sur l'ancien rendu ne correspond plus. Elle n'est calculée que pour les spans réellement édités ou en cours d'édition — le faire pour tous les spans de toutes les pages était du travail pur perte. L'aperçu est `overflow-hidden` : un texte plus large que sa boîte est rogné au lieu de déborder sur le contenu voisin (l'export, lui, le réduit via `fitted_fontsize`). Le dialogue « Versions » de l'éditeur est en `sm:max-w-3xl` (5 boutons d'action par ligne), celui de « Mes documents » en `sm:max-w-2xl` : la largeur `sm` par défaut ne laisse rien au nom/métadonnées.
- Chargement du PDF : `getDocument` reçoit un `onProgress` qui alimente `loadProgress` ; tant que `pdfDoc` est nul, `PdfLoadingProgress` affiche une barre shadcn (`components/ui/progress.tsx`, Base UI) avec les octets reçus / total, et chaque page garde son `Skeleton` jusqu'à son premier rendu. `total` vaut 0 quand la réponse n'a pas de `Content-Length` → barre indéterminée (`value={null}`), on n'invente pas de pourcentage. Utile dès ~15 Mo : sur un lien 3 Mb/s le document met ~30 s à arriver.
- Désélection : cliquer une zone non éditable de la page (le canvas lui-même, ou le cache blanc `data-page-backdrop` d'une image déplacée) vide `selection`/`editingId`/`croppingId` (`clearSelection`). Sans ça les poignées de géométrie restaient collées au dernier élément édité indéfiniment — et interceptaient les clics visant ce même élément (un `button` de span est recouvert en son centre par la poignée `e`/`w` de son propre `GeometryOverlay`). Le test d'appartenance est une **égalité d'identité** avec le canvas, pas un `closest()` : les poignées émettent aussi un `click` qui remonte, et l'annuler effacerait la sélection à chaque redimensionnement.
- Granularité de sélection mot par mot : ce n'est **pas** un défaut d'extraction. Un producteur qui justifie une ligne positionne chaque mot individuellement, donc `get_text("dict")` rend un span par mot (mesuré sur `G-PRO-600_written_report.pdf` : 33 et 43 spans pour une ligne justifiée, 1 seul span pour une ligne non justifiée / dernière ligne de paragraphe). Fusionner les spans d'une ligne rendrait l'édition plus confortable mais **détruirait la justification à l'export** (`TextWriter` réécrirait la ligne avec des espaces normaux) — arbitrage non tranché, ne pas « corriger » l'extraction sans le décider.
- Zoom & versions dans l'éditeur (étape 8) : zoom interne (état `zoom`, largeur du wrapper = `BASE_PAGE_WIDTH*zoom`, canvas re-rendu à la résolution affichée, calque en % donc aligné nativement — conteneur `overflow-x-auto`). Dialogue "Versions" alimenté par `getDocumentVersions` (passé à `PdfEditor` par la page éditeur). Le panneau "Modifications" est cliquable (sélection + scroll). Export → téléchargement auto (`triggerDownload` de la route `/download`) puis ouverture de la nouvelle version.
- Suppression de version : `DELETE /api/documents/[id]/versions/[versionId]` (`app/api/documents/[documentId]/versions/[versionId]/route.ts`) — cloisonné par `userId`, refuse (409) de supprimer s'il ne reste qu'une version, supprime la ligne + le fichier sur le volume. Deux points d'entrée UI : dialogue "Versions…" de "Mes documents" (`documents-view.tsx`) et dialogue "Versions" de l'éditeur (`pdf-editor.tsx`, qui redirige vers la version la plus récente restante si la version supprimée était celle ouverte). `sourceVersionId` n'a pas de contrainte FK (simple traçabilité) donc rien à nettoyer côté versions qui en dérivent. La suppression retire aussi le journal (`journalPath`).
- Journal d'édition persistant (reprise des modifications) : chaque export écrit le journal qui l'a produit dans `<versionId>.json` **sur le volume, à côté du PDF** — jamais en base, il transporte les images de remplacement en base64 (`journalRelativePath`) ; la ligne `document_versions` n'en garde que `journal_path` + `edit_count`. Un échec d'écriture du journal ne fait pas échouer l'export (`journal_path` reste NULL). Lecture par `GET /api/documents/[id]/versions/[versionId]/journal` (cloisonné par `userId`). Reprise : `…/versions/<sourceVersionId>?restore=<versionId>` — l'éditeur rejoue le journal **sur la version source** en modifications *en attente* (`edits`/`spanBoxes`/`imageEdits`), pas sur la version exportée où les changements sont déjà cuits ; les ids de span/image sont stables pour un fichier donné, donc l'appariement tient, et les entrées orphelines sont comptées et signalées. Le paramètre `?restore` est retiré de l'URL après coup (`router.replace`), sinon un rafraîchissement écraserait les modifications faites depuis. Deux points d'entrée : bandeau « Reprendre ces modifications » sur la version ouverte, et un bouton par ligne du dialogue « Versions » (affiché seulement si la version source existe encore). Le dialogue « Versions » de « Mes documents » ne l'expose pas encore. `imageBase64` ne porte pas son type MIME : `dataUrlFromBase64` le renifle (`/9j/` → JPEG, sinon PNG).
